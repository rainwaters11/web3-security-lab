LEARN THE BUILDING BLOCKS

Parts of this smart contract

Open one part at a time. Read its meaning, then find the example in the contract below. This reference stays available in every support mode.

1. Contract name and bodycontract SharedVault { ... }

The contract is a program on the blockchain. Its name is SharedVault. Curly braces group the data and functions that belong to it.

2. Comments and license// SPDX-License-Identifier: MIT

Comments explain the code to people. The SPDX comment states the license. Comments do not execute or enforce safety.

3. Compiler rule (pragma)pragma solidity ^0.8.20;

States which Solidity compiler versions can compile this file: 0.8.20 up to, but not including, 0.9.0. This project separately pins its compiler to 0.8.20.

4. Stored data (state variables)address public curator;

State variables hold persistent contract data. address is a type for an account or contract address. curator is a name chosen by the developer; its name alone grants no permissions.

5. Address-to-balance record (mapping)mapping(address => uint256) public balanceOf;

A mapping associates keys with values. Here, each address has a recorded unsigned integer balance, measured in wei by this contract. uint256 is a nonnegative whole number. balanceOf is a developer-chosen name; it is separate from the vault’s actual ETH balance.

6. Setup (constructor)constructor() { curator = msg.sender; }

The constructor runs during deployment. Here it stores the deploying caller as curator. It is not a function users call again after deployment.

7. Actions (functions)deposit() · withdraw(uint256 amount) · changeCurator(address next)

Functions describe actions the contract can perform. deposit records incoming ETH, withdraw requests an ETH payment, and changeCurator assigns an address. Read each body to see its actual checks and effects.

8. Inputs and temporary variablesuint256 amount · address next · bool ok

Parameters are inputs to a function. amount is a number; next is an address. The local bool named ok stores a true/false result during this call. These names are chosen by the developer.

9. Who can call and pay (keywords)public · external · payable

external functions can be called from outside the contract. public state variables get generated read functions; public does not mean only the owner may use them. payable lets a function accept ETH. These keywords do not replace permission checks.

10. Caller and attached ETHmsg.sender · msg.value

msg.sender is the immediate caller of the current call. msg.value is the ETH attached to that call, in wei. A contract can be the caller. One ETH equals 10^18 wei.

11. Checks and failuresrequire(condition, "message");

require continues only if its condition is true; otherwise the call reverts. A revert undoes changes in the failed call and its nested calls. If a caller catches that failure, other work in the caller can continue. Solidity 0.8 checked arithmetic can also revert.

12. Calls and data updatesmsg.sender.call{value: amount}("") · += · -= · =

The low-level call attempts to send ETH and can execute code at the recipient. It returns a success flag and return data. The assignment operators add to, subtract from, or replace a value. Follow their order in the code when tracing execution.

Other parts you may see in future contracts
Events
Logs that applications can read to learn what happened.
Modifiers
Reusable logic placed around a function body, often used for checks. Their actual code determines the protection.
Custom errors
Named error types a contract can use when reverting.
Structs and enums
Types for grouping related data or naming a set of choices.
Imports, inheritance, interfaces and libraries
Ways to organize, reuse or describe code across contracts and files.
receive and fallback
Special entry points a contract may define for incoming calls. receive handles empty call data; a payable fallback can accept ETH when no other entry point matches.

These parts are not declared in SharedVault. A contract does not need every part on this list.

What is a prediction?

Your best explanation of what will happen before you see the outcome. Name the caller, the amount, whether the call succeeds or reverts, and why. It is okay to revise your understanding after checking evidence.

What is an invariant?

A rule that should hold at a stated checkpoint. Ask: whose funds or permissions must be protected, and when should I check the rule? Write the rule in your own words; a later test checks whether it holds.

After testing: add evidence and explain the trace
What counts as evidence?

Record the exact command, test name, code version, tool versions, and actual result. If you have not run a test, say “not run.” A prediction, animation, or AI explanation is not an executed trace. A passing test supports only its checked path.

How do I explain a trace?

A trace is a step-by-step record of execution. Identify the caller, checks, external calls, state updates, and any failure. Explain which call’s changes were rolled back and what the final state shows. Describe the limits of the evidence.
